## 一、FE-01：管理表空槽

**原因（读 PixiJS 8.22.0 源码，并在两个构建上实测）：**
- Pixi 8 把它管理的每个 GPU 资源和可渲染对象，按 uid 放进 GC 系统登记的哈希表（`GCManagedHash.items`）。资源释放时，表里对应的值改成 `null`，键还留着。
- 只有在渲染期间，且一张表攒满 10,000 个空槽时，Pixi 才会重建这张表、去掉空槽。
- 整页复用一个渲染器（第四轮的做法）以后，每局卸载视图释放的东西都在停放的渲染器里留下空槽。
- Astra 报的是 Graphics 那张表。实测**一共有六张表在长**，同一个探针在两个构建上的结果：

| 表 | 基线 `5b09c05`：20 次重挂后 / 结算停放后的空槽 | 修复后 |
| --- | --- | --- |
| graphics（Graphics 渲染对象） | 161 / 169 | 0 / 0 |
| graphicsContext | 161 / 169 | 0 / 0 |
| glBuffer | 280 / 294 | 0 / 0 |
| glTexture | 227 / 242 | 0 / 0 |
| glGeometry | 140 / 147 | 0 / 0 |
| tilingSprite | 40 / 42 | 0 / 0 |

两边的存活项完全相同（挂载时 graphics 8、glBuffer 19、glTexture 17 等；停放时 glBuffer 5、glTexture 2、glGeometry 2）。修复没有动任何存活资源。[基线探针](evidence/slots-base.json)、[修复后](evidence/slots-fixed.json)。

**修复（`host.ts` 的 `compactManagedHashes`）：**
- 停放渲染器时，对 GC 系统登记的每张表做一次 Pixi 自己在阈值时做的同样操作：把非空项复制进一张新表，替换旧表。
- 只丢 `null` 占位，不碰任何存活项；正在渲染（`_running`）时不做。

**风险：** 这里读了 Pixi 的内部字段 `renderer.gc._managedResourceHashes`，依赖锁定的 8.22.0。字段不存在或形状变了时，函数什么也不做，返回 0，不会报错。这种情况会被门禁发现：样板门禁 W11、W12 现在按同样的表统计空槽，表不再被清理时就会失败。

**证据：**
- **样板门禁：**
  - W11：20 次视图重挂后空槽 3 → 0，存活项 59 = 59。
  - W12：真实结算停放后空槽为 0。
- **命名包快照，Astra 原工具 `astra-r7-cache-graph.mjs`：** 第 6/20/40/60 轮，Graphics 表的索引键：

| 构建 | 第 6 轮 | 第 20 轮 | 第 40 轮 | 第 60 轮 |
| --- | ---: | ---: | ---: | ---: |
| 基线：键数（全为 null） / backing B | 144 / 3,096 | 480 / 12,312 | 960 / 24,600 | 1,440 / 49,176 |
| 修复后：键数 | 0 | 0 | 0 | 0 |

基线这一行与 Astra 的表逐项一致，说明是同一现象。[基线](evidence/cache-base.json)、[修复后](evidence/cache-fixed.json)。

这里证明的是：在同一工作负载、这四个采样点上，空槽不再随循环增加。没有依赖或验证 Pixi 的 10,000 阈值；修复不靠它。

## 二、FE-02：停放渲染器的事件池引用旧 HUD

**原因：**
- 样板从不使用 Pixi 的联邦事件（federated events）：所有输入由 `input.ts` 直接读 DOM。
- 但 Pixi 的事件系统在初始化时会挂上，并在画布、document、window 上监听指针事件。
- 它的事件池和根事件（`_rootPointerEvent` 等）一直保留最后一个原生 PointerEvent，而这个事件的路径里有当时的 HUD。
- 卸载 HUD、停放渲染器以后，这些引用仍在，所以旧 HUD 的 DOM 子树一直留在内存里。

**修复（`host.ts` 的 `detachPixiEvents`）：**
- 渲染器初始化后立即调用 Pixi 的公开接口 `renderer.events.setTargetElement(null)`，把事件系统从 DOM 上摘下来。
- 之后它不再收到任何事件，也就不再留存原生事件。
- 渲染器因上下文丢失而重建时，会对新渲染器再做一次。

**原来事件系统写在画布上的两个样式，改由 `coast.css` 保留：**
- `touch-action: none`：画布上不触发浏览器的平移和缩放；
- `cursor: inherit`：鼠标指针照常显示。

实测修复前画布上的指针是 Pixi 写的 `inherit`，计算值为 `auto`，会覆盖样式表里原有的 `cursor: none`。所以玩家一直看到的是普通指针。现在样式表直接写 `inherit`，玩家看到的不变；如果只摘掉事件系统而不改样式表，指针会突然消失。

**证据：**

| 检查 | 基线 | 修复后 |
| --- | --- | --- |
| 真实鼠标移动、点击后，事件系统是否挂在 DOM 上 | 是 | 否 |
| 根事件是否持有原生事件 | 是（结算后指向基地界面的 `overlay`） | 否 |
| 事件池里带原生事件的条数 | 3 | 0 |
| 命名包快照第 6/20/40/60 轮，被保留的已移除 `cs-hud` | 每点 2 棵 | 0 |
| 快照里带原生事件的 FederatedPointerEvent | 每点 4 个 | 0 |

样板门禁 W11 在前面各步的真实拖放、点击、瞄准之后断言：事件系统未挂载，三个根事件都不持有原生事件。

另外核对过一个怀疑：Pixi 的 EventsTicker 会在指针不动时用 `Ticker.system` 补发合成的 pointermove。实测在基线上，游戏中 1 秒和停放后 2 秒内都是 0 次，所以不把它列为问题。

## 四、总堆结论（与具体修复分开）

- **F20 仍为 PARTIAL。** 原标准是正式包同口径「后段均值不高于第 6–10 轮均值」，修复后三个窗口仍分别 +348 KB、+605 KB、+797 KB。
- **两项修复去掉的部分：** 第 56–60 轮约 142 KB。强引用图里「其他 JS 与元数据」一类从 +74 KB 降到 +5 KB。
- **剩下的增长：** 第 6→60 轮强引用图约 1.03 MB，其中：
  - 编译代码约 77%；
  - 其他原生对象约 14%，含 VM 的 WeakArrayList、DOMRect 等；
  - 浏览器性能条目约 8%。
  - 这三类都没有找到指向样板对象的保留链，但也**没有证明它们会停止增长**：60 轮内编译代码仍在增加，只是在减速。
- **没有测：** 原生显存、驱动内存、音频后端，这些不在本轮签收范围内。

## 七、遗留

- **F20 总堆仍为 PARTIAL。** 剩余增长主要是编译代码，其次是 VM 原生结构和浏览器性能条目。60 轮内没有看到平台期。要签收，需要更长的循环或别的证据，证明它有上界；本轮不改判。
- **依赖 Pixi 内部字段：** `compactManagedHashes` 读的是 `renderer.gc._managedResourceHashes`。升级 Pixi 时请先跑 W11、W12；字段变了它会静默不做事，靠这两项门禁发现。
- **Pixi 事件系统已摘下：** 以后如果有人想用 Pixi 的 `eventMode`、`on('pointerdown')` 做交互，需要重新挂上并处理停放时的引用。目前样板没有这类用法。
- **原有遗留不变：** ASTRA-SAVE-01、Sol 第三轮旧可见性探针失败（基线也失败，后继探针通过）、`qol-expansion` 基线间歇失败、真机和真人 G12、原生显存/驱动/音频内存观测。
