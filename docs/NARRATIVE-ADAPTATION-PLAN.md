## 1. 输入、目标与交付边界

开工技术基线为 main `8355b857736df7fe471301d61208c25e2b7f9d61`，交付前同步至最新 main `43a342ce434c101e4b7058a54f6f29ede9482223`。剧情输入固定为 [PR #29](https://github.com/xuys2025/escape-bincov/pull/29) 的 [c940128 文稿](https://github.com/xuys2025/escape-bincov/blob/c940128e1959acb175955a30bdf6c4a81976d719/docs/MAIN-STORY.md)。2026-10-09，#29 已合并为 `43a342c`；其 `48d7fa5` 仅更新批准状态，正文不变，当前可查阅[已接受文学稿](MAIN-STORY.md)。地图、势力与主线边界沿用已接受的[世界观与地图主线](WORLD-REGIONS-STORY.md)。

目标是让每段重要剧情具有空间载体、玩家行动、人物回应和可验证结果。全局规划覆盖一处据点、十二个出击区域、六章十八节点与逃离／封潮／留守三个结局；采用主线汇合、人物有分歧的结构。本轮细化到可制作的范围是市场探索、维修物资交付、供电恢复及小蔡对话，工厂联系属于后续批次。

用户已选择：局内短交流且行动不停，回站深谈；市场使用固定维修补给；可选调查和对白不成为旧维修任务的新门槛。叙事中的第 17～61 天表示章节节奏，不与现实等待天数、十分钟行动或每局换潮周期绑定。

2026-10-09 核对时 [#22](https://github.com/xuys2025/escape-bincov/pull/22) 仍开放。按现有排期，世界观相关游戏接入在 #22 完成后推进。本轮交付文档，不提前修改源码、存档、素材或发布包。#29 负责文学稿，#22 负责美术方向，本方案承接剧情转化内容规格；三者分别验收。#26 中的持久盐度与异化建议继续按原议题讨论。

## 2. 五道制作工序

| 工序 | 主责职能 | 输入 → 输出 | 通过条件 |
| --- | --- | --- | --- |
| 剧情拆解 | 叙事策划 | 原稿与设定 → 事件卡、人物知情表、伏笔回收表 | 每条真相有来源；人物不提前知道后文；十八节点因果成立 |
| 空间设计 | 关卡策划 | 事件卡与现有地图 → 拓扑、两条路线、锚点、出口与风险 | 玩家能到达、行动并返回；信息收益或交战风险确有差别 |
| 场景与对白 | 叙事、美术、音效 | 空间与状态 → 布景变化、条件对白、声音及字幕清单 | 对白能够兑现；事实、陈述与猜测可区分；重要声音有文字对应 |
| 任务接入 | 开发 | 内容规格 → 纯逻辑条件、场景交互、联合存档与迁移 | 不重复奖励，不拆分剧情和世界的提交，不丢旧进度 |
| 联合验收 | 策划、开发、试玩者 | 可运行版本 → 规则报告、真实截图、理解反馈 | 功能、内容表达、真人理解分别有证据与未验收登记 |

先验证路线，再制作摆件与美术；确定可执行动作后再写对白。职能可以由同一人承担，这张表不要求增加并行实现线。一个批次在同一承接任务内推进，阶段提交不自动拆成多个 PR。

### 2.1 事件卡模板

稳定 ID 用 `ch01-n01` 表示主线节点，`ch01-sc-*` 表示场景，`ch01-dlg-*` 表示对白；区域、人物和证据另有登记 ID。ID 不随中文标题润色改变。

每张卡必须填写：原文章节与段落锚点、来源性质、前置知识、玩家目标及情绪、区域与空间载体、进入条件、具体动作、获得的信息、状态与后果、失败／遗漏／重访、对应验收项。来源性质取“设定事实”“人物陈述”“玩家见闻”“改编新增”。人物口述内容可以成立为“他说过”，不能直接升级为世界真相。

完整十八张事件卡见[登记册](story/CONTENT-REGISTER.md)。市场样板在[独立规格](story/CH01-MARKET-SLICE.md)中继续落到格坐标、触发及对白。

### 2.2 内容审阅

叙事策划检查因果与声音，关卡策划检查空间与路线，开发检查状态、事务和恢复；最后共同走读一次。审阅记录使用“通过／需修订／未运行／环境阻塞”，不把有了文档或 CI 通过当作玩家已经理解故事。

每次修订先修改对应事件卡，再同步场景、对白与验收引用，避免四份内容各自演化。改编新增明确标注；改变既定人物立场、剧情真相或结局代价时，在承接任务中记录具体取舍。

## 3. 地图、场景、对白与任务的转化标准

### 3.1 地图

十二个区域各保留主题：老城生活与失联、医院救治与隔离、旧院占楼生活与交涉、工厂设备与运输、实验室干燥设施中的异常、商场配给、国道道路与资格、市场冷链与供电、观测站数据与维护、灯塔庇护与封潮、港口运输、货轮打捞与货物。编号与差异表见登记册。

每区至少两条有实际差别的探索路线和一个明确主线目标，列出进入、调查／取回、返站路径。内陆以干燥路线为常态；地形、设施、视线和人员控制表达差异。普通行动不得封死所有有效返站出口。普通撤离回水产站，主线最终撤离才出县。

### 3.2 场景叙事

采用“可观察事实 → 玩家推断 → 人物解释或证据印证”。例如空钢架与搬运痕迹表明货物离开，账目才补上去向；空钢架本身不宣布母样的全部真相。

主线必要信息有可重复取得的明确载体，地图提示或任务说明能指向它；旁支生活细节允许遗漏。布景、声音、文字、行动后变化各承担不同信息，不把同一段原文复制到全部媒介。关键声音同步字幕；玩家关闭音量后仍能辨认事件。表现变化从已提交状态派生，不单独存一套“看起来完成”的状态。

### 3.3 人物对白

每人登记：所知、所求、隐瞒、愿意交换什么、说话习惯和各章变化。小蔡说设备细节，以套袖、清点和停顿表达担忧；老栓用手艺与行动表达关心；许医生区分检测结果和推测；钟队长谈责任与资格；宋姐提出具体生活需求。其余人物见登记册。

每个话题有首次、缺条件、条件满足、选择后、重复询问及退出回应。局内一至两句提示不暂停；长篇与重大选择回站展开。退出不自动选择，已提交的交付与选择不因关闭对白撤销。战斗、低血量、换潮和撤离警告先于剧情字幕显示，未显示的剧情可从见闻回顾阅读。

### 3.4 任务与人物去向

主线负责调查推进；支线改变人物处境、准备条件、意愿和后续回应。节点完成依据动作、带回物证或实际交付，不能把读完对白等同于修复、运输或救治完成。关键解锁不使用低概率掉落、隐藏善恶分数或一次措辞决定角色生死。

人物去向使用“已办事项 → 本人意愿 → 玩家明确安排 → 结局表现”表。车辆、燃油、药品、作保、证据携带各有独立用途，不折算成一个总分。后续批次必须填满对应条件表再接入；登记册中的去向机制是编写边界，不把原稿的示例表作为固定游戏结算。

## 4. 最小技术接入规格（待实现）

### 4.1 数据与事件

| 拟议类型 | 最小职责 | 数据归属 |
| --- | --- | --- |
| NarrativeNode | 前置条件、目标、完成事件、后续节点、旧任务承接 | 编译进游戏的静态内容 |
| SceneCue | ID、世界／地图与锚点、触发条件、重复策略、表现引用 | 编译进游戏；坐标不来自导入存档 |
| DialogueNode | 说话人、显示条件、文本、选项、下一话题和状态效果 | 编译进游戏；有限节点，不执行任意脚本 |
| StoryState | 已确认线索、完成节点、明确选择、人物记忆、本行动触发记录 | 与角色、物资和世界同一主档 |
| StoryEvent | 事件 ID、来源交互、runId／mapId（局内）、请求的动作 | SaveSession 校验后转换为候选状态 |

规则模块保持无 DOM／Phaser。UI 与场景发送事件；会话校验触发范围、条件、已有状态和行动身份。固定流程为：

```text
玩家交互 → 条件与来源校验 → 候选剧情及世界状态
       → SaveSession 联合写入 → 成功后发布状态及反馈
                               → 失败回滚并进入既有保护流程
```

已成功保存的见闻属于玩家知识，行动失败后仍能回顾；实体物证仍遵守背包、安全箱与死亡／超时／放弃规则。按原稿要求成功带回的主线证据，不能仅凭见闻解锁。首批只引入有限布尔条件和话题选择，不实现通用脚本语言、护送 AI 或动态县城模拟。

### 4.2 版本、迁移与事务

基线主档键为 `escape-bincov.session.v2`，外层记录版本为 3／4。叙事接入拟新增外层版本 5，完整恢复备份同步支持 5；实施前重新核对最新主线是否已占用该版本，不因编号冲突覆盖其他迁移。

剧情存入同一记录，不另起 localStorage 键。迁移保留迁移前原始字节，与已有 legacy／migration／systems 备份不混用；未知、损坏或不兼容数据拒绝写入。旧客户端应拒绝版本 5；新客户端导入旧完整备份时迁移并确认覆盖，不以只含 profile 的备份静默清除已有剧情、RPG 或活动世界。

旧 `repair` 完成状态承接供电与对应主线节点；旧 `sample`、`ledger` 只承接已交付事实，不推定医院检测、货轮调查等新节点完成。旧任务奖励不重发，现场见闻与人物选择不补造。活动旧地图继续按旧定义恢复；新叙事世界只用于新行动，旧定义保留在 resolver 中。

开容器、取物、记录见闻、报告和选择均经过会话提交。取物与容器余量、剧情与对应世界变化同事务写入；失败不显示成功或播放完成音效。保留多窗口写入所有权、pendingSettlement、导入校验及重试幂等性。

### 4.3 接入顺序

| 阶段 | 完成条件 | 本轮状态 |
| --- | --- | --- |
| 内容规格 | 三份文档、十八事件卡、人物与伏笔表、市场路线和完整对白／状态／验收表 | 已编写，文档检查以交接记录为准 |
| 基础能力 | 纯逻辑叙事、条件对白、回顾、版本迁移与联合事务检查 | 待 #22 后排期 |

## 5. 验收与证据

本轮文档验收检查本地及固定提交链接、十八节点／十二地区／三结局覆盖、ID 与前置引用、市场坐标和路线、完整对白分支、补给算例、表格／围栏和 Git 差异。此类检查不是游戏运行验收。

未来游戏接入执行 `pnpm test`、`pnpm package`，及浏览器、UI、存档、搜刮、建筑、RPG 系统和移动风险回归；CI 保留当前完整门禁。市场样板有逐项编号的[未来验收矩阵](story/CH01-MARKET-SLICE.md#7-验收矩阵未来实施门槛)。提交 1280×720、1920×1080 与手机横屏真实截图，标注测试夹具，不能把拓扑图当实现截图。

自然计时试玩至少记录：行动种子、起点、所走路线、读字时间、完成目标／返回时间和中途风险。玩家无需读可选长对白也能完成维修；主动探索者能说清“为何找维修件、总闸说明了什么、尚不能确认什么”。自动玩家不能代替真人理解、平衡或真机；各项分别登记。
