# 敌人基础层：存档兼容基线与后续升级契约

对应 [Issue #78](https://github.com/xuys2025/escape-bincov/issues/78) 的 EN-03 首批。基线 `8ef783f`；本批只增加兼容回归、记录现有边界和后续升级条件，**没有实现新存档 schema、增援或十八原型的正式生成**。

## 本批保持的边界

现有活动敌人的持久 ID 仍是 `scav`、`salt`、`creature`、`elite`。它们不是新目录十八原型的别名；新目录的名称、阵营、武器分类不能反向改写旧档 ID，也不能据此重新生成旧行动。旧 `salt`/`elite` 的历史身份由旧 profile 保留，不能按新文案猜测成某个十八原型。

会话仍是 `SessionRecord.version` 3/4，沿海检查点 version 2，分层行动 version 1/2；扩展状态 version 1/2 的原有升级路径不变。目录增加或代码提取不构成升级理由。生成 seed、消费随机数次序、检查点 `rng`、`nextEntity`、敌人 `uid`、人口和名册不变。

现有状态包括敌人位置、朝向、生命、home/target、五态 AI、timer/cooldown/repath/alert、path；分层另有地图归属、roster 和 pursuit 的完整路线/计时。持久化读写不能借重建展示对象重抽随机数。Runtime 恢复仍按原逻辑规范化朝向；这里不承诺浮点角度的原始文本逐字节相等。

严格边界不同：分层敌人实行字段白名单，classic 的历史校验器不拒绝所有额外字段。本批没有扩大 classic 校验规则，也不把这项历史限制描述成已修复；新 ID 在两条路径均被拒绝。

## 后续升级契约（尚未实施）

### 何时升版本

十八原型首次进入正式生成、允许已有实体改变原型语义、增加可恢复行为字段，或改变人口/名册/增援不变量时，必须先做显式 schema 升级。单纯重命名目录文案、展示投影和不改变行为的代码提取不升级。

下一次有上述变化的方案应使用新的会话版本（候选为 5），并为受影响的分层行动引入新版本（候选为 3）。扩展状态本身字段改变时再升级其版本；classic 若保持旧格式继续用旧解码器，若也接受新字段则必须单独升检查点版本。具体版本号在实施时核对最新主线后确定，不可抢占别的任务版本。

迁移必须由旧版本专用校验器先验证完整旧记录，再建立独立候选；不得在同版本宽松接收新字段。活跃旧行动默认按旧行为档完成，十八原型从新行动开始；若将来确需迁移活动行动，应明确映射每个原型与状态，证明 ID、人口、掉落、装备、收益、路径与 RNG 不重抽，否则拒绝迁移并保留原档。

### 人口、名册与增援

现有分层名册长度和全体地图/追击敌人数都必须等于 `world.enemyCount`，死亡实体仍在名册中，kills 等于死亡数。未来增援不能简单放宽长度上限或复用死亡敌人的 UID。

新格式应分清初始名册、已生成增援与尚未触发的增援计划，并给每批增援持久的唯一事件 ID、原型/数量、触发状态、生成计数与下一实体序号。活体、死亡实体和 pursuit 中的每个 UID 必须在同一行动登记且恰有一个所有者；统计边界和总量上限在校验器中明确，阵营/布局不能作为跳过守恒的理由。一次触发成功后重复恢复、重复提交不得再次生成；未提交的触发不得提前写入名册。

### 可恢复字段

凡会改变下一帧决策、伤害、消耗或随机数顺序的字段必须进入完整检查点：原型及行为版本、敌我/警戒状态、目标与最后感知位置及其时间、弹匣/换弹、攻击阶段/冷却、巡逻进度、持续效果、群体命令/报警与已触发增援、追击归属和计时。实际新增字段按具体机制确定，不把这份清单当作已存在接口。

每个字段都要有单位、有限值范围、引用存在性、默认/迁移规则，并同步初始化、严格校验、capture、restore、备份导入、失败回滚。可重算的纯展示信息不用入档；重算不得消费 gameplay RNG。多个随机流如被引入，需保存各自状态并明确旧单流迁移语义。

### 旧客户端拒绝与字节保留

先用固定历史客户端及其真实存档做拒绝验证：新版本必须在旧客户端写入前被判为不兼容，提供原始备份，不能静默剥离字段或重置世界。当前 decoder 拒绝未知 session version，但不能由此推断所有历史发行版都安全。

只有固定历史客户端验证同键拒绝后，才可继续使用当前主档键。若有旧客户端会覆盖未知版本，先设计隔离的新键/能力栅栏与一次性原字节备份，再实施升级；不把无条件换键当作成功迁移。任何失败、未知原型/版本或损坏数据均保留原始字节，备份不得通过解析后重新序列化冒充原文件。

### 事务提交边界与上线门槛

所有变化沿 `SaveSession` 的独立候选 → 严格校验 → `RecoveryStore` 修订比对 → 单次记录写入 → 成功后发布。角色资源、敌人状态、名册/增援事件、尸体/掉落、弹药、任务/训练、RNG 与世界快照必须一起提交。不能先存增援事件再存敌人，也不能先发奖励再补世界。失败保留已提交世界，候选供同一事务重试或导出；冲突不强制覆盖，重试不重新抽签、不重复发奖。

未来正式接入前须新增旧客户端拒绝及迁移反例、所有世界布局和 pursuit 往返、增援触发前后重开、失败重试/重复提交/多窗口、损坏原始字节保留与真实文件导入回归。通过新 schema 与兼容性门槛之前，目录记录始终不能成为正式出生表。
